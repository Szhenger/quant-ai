# Abstractions

> An overview of every layer QuantAI is built on: the programming languages, the web
> frameworks, the external libraries, and the backend systems — what each one is, what
> job it does here, and where in the repository it earns its keep.

QuantAI is two applications sharing one contract: a **Python backend** (`backend/`) that
computes indicators, evaluates user-defined conditions, and delivers alerts; and a
**TypeScript console** (`frontend/`) that lets a person author those conditions and watch
the results in real time. Everything below is in service of that split.

---

## 1. Programming languages

| Language | Where | Why it's the right tool here |
|---|---|---|
| **Python 3** | `backend/` — all backend apps (`config`, `identity`, `engine`, `feeder`, `advisor`), tests | The quantitative core is numerical array work (`numpy`) and orchestration (Django/Celery); Python is the shared language of both worlds, so the z-score derived in `math/03` and the task that evaluates it live in the same file family |
| **TypeScript** | `frontend/src/` — the entire frontend | Strict typing is what makes the frontend half of the API contract *checkable*: `src/api/types.ts` mirrors the backend serializers, and `contracts.test.ts` fails to compile when the shapes drift |
| **SQL (via ORM)** | Generated by Django's ORM against PostgreSQL; no raw SQL in app code | Queries are expressed as querysets (`engine/tasks.py` builds the "due strategies" filter as a database-side duration expression) so the same code runs on Postgres in prod and tests |
| **Bash** | `tool/devdb.sh`, `Makefile` recipes, compose/CI command strings | Glue: a self-contained dev PostgreSQL for machines without Docker, and the repo's task entry points |
| **YAML** | `docker-compose.yml`, `docker-compose.test.yml`, `render.yml`, `.github/workflows/ci.yml` | Declarative topology: what runs, what depends on what, what gets checked before traffic arrives |

## 2. Web frameworks

### Backend — Django and its ecosystem

| Framework | Role in QuantAI |
|---|---|
| **Django 5** | The application chassis: ORM and migrations (`engine/models.py`, `identity/models.py`), settings (`config/settings.py`), admin, auth user model, email framework, cache framework (the Redis-backed per-strategy eval lock rides on `django.core.cache`) |
| **Django REST Framework (DRF)** | The HTTP API: viewsets and routers (`engine/views.py`, `identity/views.py`), serializers as the validation boundary for user-defined conditions (`engine/serializers.py`), cursor pagination for the unbounded alerts table, and per-scope throttling on the compute-heavy endpoints |
| **Django Channels 4** | The WebSocket layer: `engine/consumers.py` streams alerts to a workspace-scoped group; `engine/ws_auth.py` authenticates the socket with a JWT; `config/asgi.py` routes HTTP and WebSocket through one ASGI application behind an origin validator |

### Frontend — React and its ecosystem

| Framework | Role in QuantAI |
|---|---|
| **React 18** | Component model for the console: panels (`MarketsPanel`, `StrategiesPanel`, `AlertsPanel`, `ReplayPanel`), the strategy form, and the alert audit-tree detail view |
| **Vite 5** | Dev server (with `/api` and `/ws` proxies to the backend) and production bundler — vendor chunks are split so app-code changes don't invalidate the framework bundle, and the graph builder loads lazily |

| `celery` | The strategy-evaluation fleet: Beat schedules the sweep, reconciliation and retention tasks; workers run evaluations and per-channel alert delivery with retries (`engine/tasks.py`, `engine/delivery.py`) |
| `redis` (client) | Python driver underneath the broker, result backend, cache, and channel layer |
| `psycopg[binary]` | PostgreSQL driver for the ORM |
| `numpy` | The math: every indicator series — SMA, EMA, z-score, RSI, MACD histogram, volatility — in `feeder/indicators.py` |
| `yfinance` | Real market data (prices and headlines) from Yahoo Finance, no API key required (`feeder/providers.py`) |
| `requests` | Outbound webhook deliveries, HMAC-signed, redirects disabled (`engine/delivery.py`) |
| `duckdb` | Optional local Parquet bar cache (`feeder/barstore.py`); the pipeline degrades to a no-op without it |
| `anthropic` | The Claude SDK behind the AI contextualisation layer (`advisor/claude_client.py`) — bounded to 30s/1 retry and never in the critical alerting path |
| `pytest`, `pytest-django` | The backend test suite (`backend/test/`): unit, system, contract-pin, and journey tests against real PostgreSQL |

## 4. Backend systems

The runtime topology — each box is a separately-running process or managed service
(`docker-compose.yml` locally, `render.yml` in production):

```
                        ┌────────────────────────┐
   browser ── HTTPS ──▶ │  Daphne (ASGI)         │──── SQL ────▶ PostgreSQL 16
           ── WSS ────▶ │  Django + DRF+Channels │
                        └───────────┬────────────┘
                                    │ enqueue / group_send / locks / cache
                                    ▼
                        ┌────────────────────────┐
   Celery Beat ── 60s ─▶│  Redis 7               │◀── broker ── Celery workers
   (sweep, reconcile,   │  broker · results ·    │              (evaluate, deliver)
    retention)          │  cache · channel layer │                │
                        └────────────────────────┘                ├─▶ Yahoo Finance
                                                                  ├─▶ Anthropic API
                                                                  ├─▶ SMTP
                                                                  └─▶ user webhooks
```

| System | Role |
|---|---|
| **PostgreSQL 16** | The system of record: users, workspaces, strategies, alerts (with their evaluated-condition audit trees), JWT blacklist. Row locks (`select_for_update`) and single-transaction alert+cooldown writes are why a crash can't split an alert from its cooldown stamp |
| **Redis 7** | Four jobs in one service: Celery **broker**, Celery **result backend** (results expire after 1h), the shared **cache** (per-strategy eval locks, fleet-wide bar/analysis/replay caches, news cache), and the Channels **channel layer** that carries alerts from workers to open WebSockets |
| **Celery worker fleet** | Executes `evaluate_strategy` (with `acks_late`, under a TTL'd per-strategy lock) and per-channel `deliver_alert_channel` tasks with exponential-backoff retries |
| **Celery Beat** | The clock: sweeps due strategies every 60s (database-side due filter + compare-and-set claim), reconciles undelivered alerts every 5 minutes, prunes old alerts and expired tokens daily |
| **Daphne / ASGI** | One server process for both protocols; sync DRF views run on a threadpool, WebSocket consumers run async |
| **Yahoo Finance** (external) | Primary market-data source, wrapped in `ResilientProvider`: any failure degrades to deterministic synthetic data flagged `synthetic=true` end-to-end |
| **Anthropic API** (external) | AI contextualisation of fired conditions — structured verdicts with confidence; outages fail open so quantitative alerting never depends on it |
| **SMTP** (external) | The email alert channel (console backend in DEBUG, real SMTP in production, 10s timeout) |
| **Docker Compose** | Local topology with healthchecks, loopback-only DB/Redis ports, and restart policies; `docker-compose.test.yml` runs the suite against a throwaway Postgres |
| **Render** | Production hosting: web service (API), worker, Beat, managed Postgres and Redis (`noeviction`), and the static console site — secrets injected, never committed |
| **GitHub Actions** | CI: the backend suite + migration-drift check in containers, and the frontend test + type-check + build, all read-only permissions |

## 5. How the layers meet: the contract seams

Three seams keep the stack honest, and each has an executable pin:

1. **REST/WS wire shapes** — `backend/test/journeys/fixtures/*.json` is the single
   source of truth. `backend/test/journeys/test_contract_fixtures.py` proves the live
   API produces those shapes; `frontend/src/api/contracts.test.ts` proves `types.ts`
   matches the same files. A serializer change must update both sides in one PR.
2. **The indicator catalog** — `GET /indicators/` describes every indicator (label,
   unit, parameter defaults, default threshold, help text), and the console builds its
   strategy form from it. Adding an indicator server-side surfaces it in the UI with no
   frontend change.
3. **Data honesty** — the `synthetic` flag travels with every price series from
   `feeder/providers.py` through alerts, analysis and replay payloads to the UI badges,
   enforced by `backend/test/journeys/uxspec.py`. No layer may present fabricated
   fallback data as real market data.
